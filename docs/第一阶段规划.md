## 一、阶段目标

**在零业务逻辑的前提下，跑通「启动 → 主菜单 → 四个模块窗口 → 读写数据 → 打包成 exe」这条完整链路。**

第一阶段结束后，所有与游戏规则无关的技术不确定性都应消失。

---

## 二、为什么单独切出这一阶段

策划方案 §8.3 把「地图可编辑保存」和「敌人走到蓝门」压在同一周，那是**把架构风险和业务逻辑混在一起**——一旦中途发现窗口、字体、路径哪里不通，已经写好的规则代码要跟着返工。

因此本阶段**刻意不含任何游戏逻辑**，四个模块窗口里只有占位 UI。

### 4.2 各交付物职责

#### `pom.xml`
- `maven.compiler.release = 17`
- 依赖 `org.processing:core:4.5.6`
- 依赖项目内本地仓库的 `g4p:4.3.11`
- 依赖 JUnit 5（test scope）
- 配置 `maven-shade-plugin` 打可执行 jar（供 `jpackage` 使用）

#### `common/ui/WindowManager.java` —— 本阶段技术含量最高的一块

统一管理模块窗口的创建与显示：

```java
WindowManager.open(owner, ModuleKey.MAP_EDITOR);   // 已存在则唤起，不存在则创建
WindowManager.hide(ModuleKey.MAP_EDITOR);          // 隐藏而非销毁，保留状态
WindowManager.isOpen(ModuleKey.MAP_EDITOR);
```

要点：子窗口关闭行为一律设为「隐藏」，从根本上规避关窗杀进程的问题。

#### `common/util/UITheme.java`

```java
UITheme.apply(applet);                                  // 每个窗口 setup 时调一次
UITheme.button(applet, "saveMap", "保存地图", 20, 20, 150, 32);
UITheme.spinner(applet, 20, 90, 150, 28, 100, 0, 999);
```

封装四件事：
1. `GCScheme` 自定义暗色配色
2. `G4P.setDisplayFont / setInputFont / setSliderFont` 注入中文字体
3. **`GLabel` 显式设色**（实测默认色在深色背景下对比度不足）
4. `pixelDensity(1)`（规避 R5）

#### `common/io/FilePaths.java`

```java
FilePaths.readResource("data/enemies.json");   // classpath，只读
FilePaths.mapFile("map_001");                  // <工程根>/data/maps/map_001.json，可写
FilePaths.levelFile("level_001");
FilePaths.ensureDataDirs();                    // 首次运行创建目录
```

#### `Stage1SmokeTest.java` —— 用 JUnit 替代「自检按钮」

```java
@Test void 资源数据可读取()      { /* operators.json / enemies.json */ }

@Test void 地图契约正确() {
    // version = 1
    // cols = 12, rows = 8, tileSize = 64
    // legend["-1"] = "empty"        ← 重点：负数当 key
    // tiles 维度 = 8 行 × 12 列
    // redDoors / blueDoors 解析正确
}

@Test void 坐标换算正确() {
    // (0,0)  中心 → (32, 32)
    // (11,7) 中心 → (736, 480)
}

@Test void 可写数据目录能创建()  { /* data/maps、data/levels */ }
```

**用 JUnit 而不是自检按钮的理由**：这些是纯逻辑验证，JUnit 可重复执行、可在 CI 跑、并作为课设「测试」章节的素材。窗口相关的验证本质上是 GUI，靠人工。

## 九、动手前须定型的一项：窗口机制

在 Maven 环境下有两条路，**必须先做对比实验**：

| 方案 | 机制 | 验证状态 |
| --- | --- | --- |
| **A** | `PApplet.runSketch(String[], PApplet)`，每个模块是独立的 `PApplet` 子类 | ✅ **已实测通过，采用** |
| **B** | G4P `GWindow.getWindow()` + 绘制回调，所有控件挂在主 PApplet 上 | 控件正常；**但模块窗口类就不是 `PApplet` 子类了** |

**实验要点**：两种方案各写一个最小工程，回答两个问题——

1. 子窗口上的 G4P 控件能否正常渲染？
2. **关闭子窗口后，主窗口是否存活？**

第 2 问是决定性的。若两方案都可行，**优先选 A**：它与策划方案 §10.1.4「各模块窗口类继承 `PApplet`」一致，类结构更自然。

### 9.1 结论（已回填）

**采用方案 A。** 在正式工程中实测：

- 启动窗 `SplashScreen` 通过 `PApplet.runSketch` 成功拉起主窗口 `LauncherApp`，
  窗口标题 `YesterCar — 主菜单`；
- 主窗口上 4 个 G4P 中文按钮创建成功，G4P 无任何警告；
- 启动窗随后 `surface.setVisible(false)` 隐藏，主窗口存活。

**验证方法留档**：窗口是否真的打开，靠 `EnumWindows` 枚举进程顶层窗口 + 读窗口标题确认，
而不是「点了没报错就算过」。中途正是靠这个方法发现了「窗口对象已创建但渲染循环被异常打断」
的假成功（详见交接文档 §4.2）。

结论已回填到交接文档 §6.1；策划方案 §10.1.4 仍待同步。

### 10.3 计划外但值得记下的收获

1. **G4P 的实际 API 与官方文档/示例不一致**：`GButton` 没有 `setActionCommand`（要用 `tag` 字段），
   按钮回调名固定为 `handleButtonEvents`。写错时**只是控制台一句提示，按钮毫无反应**——
   这类「静默失败」最容易在整合期浪费整天。
2. **G4P 默认调色板数值已逐格提取留档**（交接文档 §4.5），后续精调配色不必再靠猜。
3. **`.mvn/maven.config` 的平台字符集陷阱**：文件里写了中文注释，Maven 连启动都做不到。
4. **验证 GUI 要有可判定的证据**：用 `EnumWindows` 读窗口标题，才能区分「真的开了」和
   「对象建了但渲染死了」。

2. `jpackage` 打 exe 并在 exe 上重跑上述验收；
3. 企划方案 §10 的包名同步为 `com.yestercar`。
