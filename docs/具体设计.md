## 1.5 ⚠️ 环境陷阱清单

按「踩到就浪费半天」排序。

### ① `JAVA_HOME` 默认指向 JDK 11，**不能用**

```
JAVA_HOME = D:\A\jdk-11.0.25      ← 系统默认，Processing 4 不支持
```

三条措施已就位：`pom.xml` 里 `<maven.compiler.release>17</maven.compiler.release>`；
`tools\*.cmd` 自动切 JDK 17；IDEA 项目 SDK 已设为 17。

> 补充：PATH 上的 `java` 其实是 17.0.12，只有 `JAVA_HOME` 指向 11。
> 所以 `java -version` 看着没问题，**但 Maven 用 `JAVA_HOME`，仍会失败**。

### ② `.mvn/maven.config` 用**平台字符集**解码，写中文会让 Maven 直接崩

```
java.io.UncheckedIOException: java.nio.charset.MalformedInputException: Input length = 1
    at org.apache.maven.cli.MavenCli.cli(MavenCli.java:386)
```

Maven **连启动都做不到，连 `pom.xml` 都没读到**，且报错完全不提示是哪个文件。

> **规定：`.mvn/maven.config`、`tools/*.cmd` 一律保持纯 ASCII，中文注释只写在 `.md` 与 `.java` 里。**

### ③ G4P 不在任何 Maven 仓库上，且**阿里云镜像会劫持 file:// 仓库**

G4P 只走 SourceForge（不可达），阿里云 public 仓库也没有 `org.g4p`。
原本按「项目内 `file://` 仓库」引入**行不通**——本机 `~/.m2/settings.xml` 里有
`<mirrorOf>*</mirrorOf>`，连 `file://` 一起劫持，报
`Could not find artifact org.g4p:g4p:jar:4.3.11 in aliyunmaven`。

**现行方案**：装成**本地仓库布局**（`.mvn/repo`，与 `~/.m2/repository` 同构）。
Maven 对已存在于本地仓库的构件不发远程请求，镜像无法干扰。
`pom.xml` 因此**不需要** `<repositories>`，G4P 就是一条普通依赖。

#### 装进**两个**仓库，否则 IDEA 报「程序包 g4p_controls 不存在」

`tools\install-g4p.cmd` 同时装两处，这是刻意的：

| # | 仓库 | 谁在用 |
| --- | --- | --- |
| 1 | `.mvn/repo`（项目内） | `tools\build.cmd` 与命令行构建 |
| 2 | `%USERPROFILE%\.m2\repository`（全局） | **IntelliJ IDEA** |

原因：**IDEA 默认忽略 `.mvn/maven.config`**，走全局仓库。只装项目内仓库时命令行正常、
IDEA 报 `java: 程序包g4p_controls不存在`。装完在 IDEA 执行
**Maven 工具窗口 → Reload All Maven Projects**。

#### `.lastUpdated` 与 `_remote.repositories` 会让「明明装了却解析不到」

| 文件 | 含义 | 后果 |
| --- | --- | --- |
| `*.lastUpdated` | 一次**失败的远程查找** | 有效期内不再重试，直接报找不到 |
| `_remote.repositories` | 构件**来源仓库 ID** | ID 与当前上下文不匹配时拒绝使用 |

本项目实际踩到过：早期探测「阿里云有没有 G4P」失败，在全局仓库留下
`g4p-4.3.11.jar.lastUpdated`，之后即使装入 jar 仍解析失败。
安装脚本第 3 步会清理这两个文件，**不要手动跳过**。

正常状态（应只有两个文件）：

```text
.mvn\repo\org\g4p\g4p\4.3.11\g4p-4.3.11.jar
.mvn\repo\org\g4p\g4p\4.3.11\g4p-4.3.11.pom
```

### ④ PowerShell 5.1 的 `Set-Content -Encoding UTF8` 会写 BOM

BOM 导致 `Syntax error on token "Invalid Character"`。
源文件一律 UTF-8 无 BOM；必须命令行生成时用：

```powershell
[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))
```

### ⑤ 控制台显示的「中文乱码」多半是假象

PowerShell 用 GBK 解释 JVM 输出的 UTF-8 字节，`=== YesterCar 启动 ===` 显示成
`=== YesterCar 鍚姩 ===`。**文件本身是好的**。不要因此把文件「转成 GBK」——那才会真弄坏。

### ⑥ `.gitignore` 里绝对不能写 `*.jar`

`third_party/G4P/library/G4P.jar` 是全项目**唯一**的 G4P 来源。
`.mvn/repo/` 已忽略（上百 MB，可重建），但 `third_party/G4P/` 必须入库。

# 第二部分　架构与公共设施

## 2.1 总体架构

**Maven 标准 Java 工程 + Processing 渲染层**：全部功能由 Java 实现、按包分层；
Processing 的 `PApplet` 只承担渲染（启动动画 / 编辑器 / 战斗画面）。

**双入口**（决策）：一个工程、一套源码、两个 `main`：

```text
com.yestercar.GameMain        ← 游戏本体
com.yestercar.EditorMain      ← 战役编辑器
```

**为什么不用 Maven 多模块**：两个应用都要用 `Workspace`/`Director`/`UITheme`/`AssetPaths`/JSON 契约。
若拆成两个独立工程，这些类会各有副本，而**地图与关卡 JSON 的读写、坐标换算、贴图命名必须两边完全一致**，
各写一份必然格式漂移且极难排查。多模块能解决副本问题，但要多维护 3 个 pom 与模块间依赖顺序，
对两人 / 4 周的课设不划算。

**交付形态**：一个 fat-jar + 参数切换。`pom.xml` 的 `mainClass` 指向 `GameMain`，
它最先判断 `--editor` 并转发给 `EditorMain`。好处是演示时不用解释「该双击哪个」。

### `common/util/Director` —— 朝向与攻击范围契约（✅ 已实现，**冻结**）

策划 §3.3 的攻击范围一律以「朝右」为基准书写，部署到其它朝向时要旋转：

```java
public int[] rotate(int baseDx, int baseDy) {
    return switch (this) {
        case RIGHT -> new int[]{baseDx, baseDy};
        case DOWN  -> new int[]{-baseDy, baseDx};    // 顺时针 90°：(x,y) → (-y,x)
        case LEFT  -> new int[]{-baseDx, -baseDy};
        case UP    -> new int[]{baseDy, -baseDx};    // 逆时针 90°：(x,y) → (y,-x)
    };
}
Director.fromDelta(dx, dy)      // 敌人朝向随移动方向；两轴都有位移时优先取列方向
```

**为什么提前到第一阶段做**：它是两人协作的接口。若不先冻结，编辑器与运行时会各写一份旋转，
对不上时极难排查 —— 「差 90°」这种 bug 看起来像美术资源画错了。

## 2.4 ⚠️ `pixelDensity()` **只能在 `settings()` 里调用**

本项目踩到的最贵的一个坑，表现为「窗口打不开」，但报错指向别处：

```
When not using the PDE, pixelDensity() can only be used inside settings().
java.lang.IllegalStateException: pixelDensity() cannot be used here
    at processing.core.PApplet.insideSettings(PApplet.java:837)
    at com.yestercar.common.util.UITheme.apply(UITheme.java:93)
    at com.yestercar.splash.SplashScreen.setup(SplashScreen.java:35)
    at processing.core.PApplet.handleDraw(PApplet.java:2055)
```

后果**不是**「密度没设成」，而是**整个渲染循环被异常打断**：窗口对象已创建、
`EnumWindows` 里能看到，但既不绘制也不响应 —— 从外面看就是「主窗口没打开」。

**正确写法**：

```java
@Override public void settings() {
    size(WINDOW_W, WINDOW_H, JAVA2D);
    UITheme.disablePixelDensityScaling(this);   // 只能在这里
}
@Override public void setup() {
    UITheme.apply(this);                        // 配色 + 中文字体
}
```

## 2.5 ⚠️ 从 jar 里列举目录**不可靠**（S2 待验证）

`getResourceAsStream` 只能按名字取，**不能列目录**；只有打成 jar 后才可用 `JarFile.entries()` 遍历。
IDEA 运行时是文件系统、打包后是 jar，**两种形态行为不同**。

「扫描 `campaigns/*/` 找出所有官方战役」正好踩在这上面。

**规避方案（推荐）**：放一份索引文件代替扫描。

```json
// src/main/resources/campaigns/index.json
{ "campaigns": ["official_01", "official_02"] }
```

用 `getResourceAsStream` 直接读，两种形态一致。代价是加官方战役时多改一行 ——
相比「IDEA 里好好的、打包后官方战役全没了」这种极难查的 bug，这个代价完全值得。

**S2 阶段先做最小验证**再定方案，不要凭猜测选。

## 2.6 窗口机制（**已定型**）

采用 **方案 A**：`PApplet.runSketch(String[], PApplet)`，每个模块是独立的 `PApplet` 子类。

| 方案 | 机制 | 结论 |
| --- | --- | --- |
| **A** | `runSketch`，模块是独立 `PApplet` 子类 | ✅ **采用**，已实测启动窗 → 主窗口切换正常 |
| B | G4P `GWindow.getWindow()` + 绘制回调 | 备选；用于同一 PApplet 内开附属面板 |

**选 A 的理由**：与策划 §10.1.4「各模块窗口类继承 `PApplet`」一致，类结构更自然。

启动窗切换主窗口的实现（第一阶段技术含量最高的几行）：

```java
private void launchMainWindow() {
    if (launched) return;                       // 幂等：draw/key/mouse 都会调
    launched = true;
    PApplet.runSketch(new String[]{"YesterCar"}, new LauncherApp());  // 新窗口 + 新动画线程
    surface.setVisible(false);                  // 隐藏而非销毁
}
```

### 关闭 = 隐藏（待实现，S4）

用 AWT 层的 `WindowAdapter.windowClosing` 拦截，比 G4P 的 `setActionOnClose` 更可靠：

```java
window.addWindowListener(new WindowAdapter() {
    @Override public void windowClosing(WindowEvent e) {
        window.setVisible(false);
        e.consume();          // 关键：阻止默认的 dispose
    }
});
```

配合 `Map<ModuleKey, PApplet>` 注册表持有窗口实例 —— **这就是「状态保留」的实现**：
实例在，编辑内容就在。主菜单按钮从注册表取实例：有就 `setVisible(true)` 唤起，没有才创建。

### G4P 的实际 API 约束（**与官方文档不一致，以源码为准**）

| 项 | 结论 |
| --- | --- |
| 多窗口 | `GWindow.getWindow(app, title, x, y, w, h, JAVA2D)` |
| **`GButton` 没有 `setActionCommand`** | ❌ 编译失败。用父类 `GAbstractControl` 的公开字段 **`tag`** 承载命令字 |
| **按钮回调名固定** | 必须是 `public void handleButtonEvents(GButton button, GEvent event)`。构造函数已自动绑定；**名字写错时 G4P 只在控制台打一句极易忽略的提示，按钮毫无反应** |
| `GLabel` 深色背景 | ⚠️ 默认色偏暗，须显式设色 → 用 `UITheme.label(...)` |
| 中文字体 | `G4P.setDisplayFont/setInputFont/setSliderFont(String, int, int)` |
| 全局配色 | `G4P.setGlobalColorScheme(int)` |
| jar 内自带 `data/` 皮肤 | ✅ 从 classpath 读，与工程自己的 `data/` 不冲突 |
| `GLabel.setText` | 定义在父类 `GTextIconBase` |

**主窗口建议拦截 ESC**（`keyPressed` 里 `key = 0`），因为 Processing 默认用 ESC 直接退进程，容易误关整个程序。

## 2.7 中文字体

本机实测可用：`Microsoft YaHei`、`Microsoft YaHei UI`、`SimHei`、`SimSun`、`DengXian`、
`KaiTi`、`FangSong`、`Microsoft JhengHei`（共 296 个字体族）。

项目统一用 `Microsoft YaHei`。**G4P 找不到指定字体会静默回退到 Arial，中文就变方块**，换字体前先确认存在。

# 第三部分　数据契约与战役结构

## 3.1 地图 / 关卡契约

沿用 `策划方案.md` §3.1、§3.2，**本次决策未做任何改动**。

⚠️ **Processing JSON 对负数 key 的行为**（实测）：`legend` 用 `"-1"` 当 key，
`JSONObject` 内部以 **String** 存 key，因此必须用 `getString("-1")`；
用 `getInt("-1")` 会抛 `RuntimeException`。`Stage1SmokeTest` 已把这条锁成断言。

## 3.2 战役：官方与自定义是同一套数据

**核心原则：一个加载器 + 两个扫描目录。**

| | 官方战役 | 自定义战役 |
| --- | --- | --- |
| 谁创作 | 开发者 | 玩家 |
| 存哪 | `resources/campaigns/`（进 jar，**只读**） | `data/campaigns/`（可写） |
| 能否修改 | ❌ 只读 | ✅ 可改 |
| 加载代码 | **同一套** `CampaignLoader` | **同一套** `CampaignLoader` |

> **禁止为两类战役各写一套加载器**。两套实现必然行为不一致，且改格式要改两处。

## 3.3 战役目录结构

```text
【只读】src/main/resources/campaigns/
  index.json                          ← 官方战役清单（见 2.5 的风险）
  official_01/
    campaign.json
    maps/map_001.json                 ← 复用契约，不改
    levels/level_001.json             ← 复用契约，不改
    textures/                         ← 可选，覆盖默认贴图
      enemies/  operators/  terrain/

【可写】<工程根>/data/campaigns/
  <玩家自建战役名>/
    campaign.json
    maps/  levels/  textures/
```

**最省事的一点**：`map_xxx.json` / `level_xxx.json` 的契约**一个字都不用改**。
战役只是给它们加了一层目录组织。

## 3.4 `campaign.json` 契约（新增）

```json
{
  "version": 1,
  "id": "official_01",
  "name": "第一关：边境哨站",
  "author": "开发者",
  "description": "教学关，敌人从西侧红门进攻。",
  "levels": ["level_001"]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `version` | int | 契约版本，必须为 1 |
| `id` | string | 战役标识，等于目录名 |
| `name` | string | 显示名 |
| `author` | string | 作者；官方战役固定「开发者」 |
| `description` | string | 简介，可为空字符串 |
| `levels` | string[] | 关卡名列表（**有序** = 游玩顺序），不含 `.json` 后缀 |

关卡与地图的关联沿用现有设计：`level_xxx.json` 的 `"map": "maps/map_001.json"`，
**相对于所属战役目录**解析。这样整个战役目录可直接拷贝分发，不用改任何路径。

## 3.5 只读战役的「另存为」规则

官方战役在 jar 里物理不可写，因此：

```text
在编辑器打开官方战役 → 标题栏显示 [只读]
        ↓ 点「保存」
提示：官方战役不可修改，是否另存为自定义战役？
        ↓ 是 → 输入新战役名
整个战役目录复制到 data/campaigns/<新名>/ → 之后编辑写入副本
```

让玩家改不坏原版，同时保留修改的可能性。

## 3.6 新增数据类

| 类 | 层 | 职责 |
| --- | --- | --- |
| `CampaignMeta` | `common.model` | `campaign.json` 的内存表示 |
| `Campaign` | `common.model` | 元数据 + 地图/关卡/贴图目录 + **只读标记** |
| `CampaignLoader` | `common.io` | 从两个根加载，含只读判定 |
| `CampaignJsonIO` | `common.io` | `campaign.json` 读写 |
| `CampaignStore` | `common.io` | 新建目录、复制、另存为 |

**只读标记来自加载来源**（resources 还是 `data/`），**不写进 json**。

# 第四部分　编辑器与运行时

## 4.1 战役编辑器为什么合并

原策划把编辑器拆成 MapEditor（地形）+ LevelEditor（波次）两个窗口。
但对玩家来说，做一张自定义战役是**一个连贯动作**：画地形 → 摆红蓝门 → 配波次 → 存盘。
切两个窗口会把这件事割裂。

**合并后：一个窗口、多栏布局、一个「保存战役」按钮。**

```text
+--------------------------------------------------------------------------+
| [新建战役] [打开战役] [保存] [另存为] [撤销]        战役: 我的自制战役  |
+--------------------------------------------------------------------------+
| 地图区（可编辑）                            | 属性栏                        |
|   +---+---+---+---+---+---+---+---+         | ┌─ 地形工具 ──────────────┐  |
|   |红 |   |   |   |   |   |   |蓝 |         | │ 不可通行 地面 高台      │  |
|   +---+---+---+---+---+---+---+---+         | │ 红门  蓝门  [擦除]      │  |
|   |   |   |###|###|   |   |   |   |         | └─────────────────────────┘  |
|   +---+---+---+---+---+---+---+---+         | ┌─ 地图参数 ──────────────┐  |
|                                             | │ 列 [12] 行 [8] 格 [64]  │  |
|   左键放置 / 右键擦除                        | └─────────────────────────┘  |
|                                             | ┌─ 关卡参数 ──────────────┐  |
|                                             | │ 初始费用 [10] 每秒回费[1]│  |
|                                             | │ 障碍费用 [3]  HP [100]  │  |
|                                             | │ 障碍数量 [9]  冷却 [5]  │  |
|                                             | └─────────────────────────┘  |
+--------------------------------------------------------------------------+
| 波次列表                                                     [+ 添加波次] |
|  ┌ 波次 1   时间 [0]                                          [删除]     ┐  |
|  │   敌人[士兵▾] 红门[0▾] 目标蓝门[0▾] 数量[5] 间隔[1.0]      [删除]     │  |
|  │   [+ 添加出怪组]                                                       │  |
|  └────────────────────────────────────────────────────────────────────────┘  |
+--------------------------------------------------------------------------+
| 状态: 已放置 红门 #0 于 (0,0)                                            |
+--------------------------------------------------------------------------+
```

### ⚠️ 合并带来的三条联动规则（原设计不存在，必须实现）

| # | 规则 | 不做的后果 |
| --- | --- | --- |
| 1 | 地图增删红/蓝门 → 波次里「红门/目标蓝门」下拉框**同步重建** | 下拉框残留已删除的门 ID，选中后存出非法 JSON |
| 2 | 出怪组引用不存在的门 ID → 标红，**保存时拦截** | 生成运行时读不了的关卡，错误暴露在交作业前一晚 |
| 3 | 改地图尺寸 → 越界的门与地形**裁剪或明确提示** | 静默丢数据；`tiles` 是二维数组，只改 `cols`/`rows` 会让 JSON 自相矛盾 |

## 4.2 运行时要点

规则细节见 `策划方案.md` §2、§5。实现上需要注意的：

| 项 | 说明 |
| --- | --- |
| 流场代价 | 静态可走无障碍 = 1；有障碍 = `1 + PENALTY`（`PENALTY = 10000`） |
| 多蓝门 | 每个蓝门一张流场，敌人出生绑定目标蓝门 |
| 重算触发 | 放置 / 摧毁 / 撤离障碍物 |
| 只重算未被阻挡的敌人 | `blocked == false`；被阻挡的锁定当前目标直到目标消失 |
| 干员选敌优先级 | `FlowField.dist` 更小者优先；相同则最早进入范围者 |
| 敌人选干员优先级 | 攻击范围内**最后部署**的干员；并列则最近 |
| 寻路实现 | **带权 Dijkstra，从蓝门反向计算** |

**先写 JUnit 再写渲染**：Dijkstra、代价计算、多蓝门、阻挡判定都是纯算法，
用测试验证比开窗口点来点去快得多。这也是策划 §1.4 选 Maven 工程而非 sketch 的核心理由。

# 第五部分　素材接口

面向**美术/平面素材**这一侧。代码侧对应 `common.util.AssetPaths`，两边必须一致。

## 5.1 最重要的规则

**贴图可以随时增量交付，缺了不影响程序运行**（策划 §2.12）：

| 情况 | 程序行为 |
| --- | --- |
| 贴图存在 | 画贴图 |
| 贴图不存在 | 画默认色块 |

所以**不需要等素材齐了才能开发**；反过来，素材丢进目录就立刻生效，**不需要改任何代码**。

## 5.2 文件放哪里

默认贴图放 **`src/main/resources/data/textures/`**：

```text
textures/
  terrain/      impassable.png  ground.png  high.png  red_door.png  blue_door.png
  enemies/      soldier.png  archer.png
  operators/    guard_01.png  sniper_01.png
```

战役专属贴图放**该战役目录下的 `textures/`**，加载优先级：

```text
战役目录/textures/... → resources/data/textures/... → 默认色块
```

## 5.3 命名规范（**硬性要求**）

文件名必须与数据文件里的 `id` **完全一致**：

| 类型 | 文件名来源 | 示例 |
| --- | --- | --- |
| 地形 | 固定 5 个名字 | `ground.png` |
| 敌人 | `enemies.json` 的 `id` + `.png` | `soldier.png` |
| 干员 | `operators.json` 的 `id` + `.png` | `guard_01.png` |

规则：**全小写**，单词间用**下划线**，只用 `a-z`/`0-9`/`_`，后缀一律 `.png`。
**不要用中文、空格、大写字母、连字符。**

现有 ID：地形 `impassable ground high red_door blue_door`；敌人 `soldier archer`；干员 `guard_01 sniper_01`。
新增时先在 JSON 里定 `id`，再按该 `id` 命名贴图。

## 5.4 尺寸规范

| 项 | 规格 |
| --- | --- |
| 格子基准 | **64 × 64 px**（与地图契约 `tileSize` 默认值一致） |
| 地形 | 64×64，必须铺满，不留透明边 |
| 敌人 | 64×64，内容居中，四周留 4~6 px 透明边 |
| 干员 | 64×64，同上；**按「朝右」画**，程序自动旋转 |
| 格式 | PNG，带透明通道（RGBA），sRGB |
| 分辨率 | 按 64 px 画即可，**不要画 256 px 再让程序缩**（会糊，且程序 `pixelDensity = 1`） |

**干员与敌人只需画一张朝右的**，不必画 4 个方向。

## 5.5 交付自查清单

- [ ] 文件名与 `id` 完全一致（全小写）
- [ ] PNG 且带透明通道
- [ ] 地形铺满 64×64，无透明边
- [ ] 干员/敌人朝右
- [ ] 敌人与干员辨识度足够

确认程序读到了：跑 `java -jar target\YesterCar.jar --check`，或直接看游戏画面。

## 5.6 界面素材（后续，当前不做）

| 素材 | 用途 | 规格 |
| --- | --- | --- |
| 主菜单背景 | `LauncherApp` | 720 × 460 起 |
| 启动画面 | `SplashScreen` | 640 × 400 起 |
| 地形工具按钮图标 | 编辑器工具栏 | 32 × 32 |
| 干员头像 | 编队/部署栏 | 64 × 64 |
| 障碍物贴图 | 运行时 | 64 × 64 |

等界面布局定下来再做，避免返工。

## 7.2 历史包袱：Processing sketch 路线的结论

已放弃，代码已删，结论保留（若将来要写 sketch）：

| 结论 | 说明 |
| --- | --- |
| sketch **不支持 `package`** | 子目录 `.java` 被静默忽略；`import xxx.Yyy` 报 `No library found for xxx` |
| `.pde` 里的类是**内部类** | 编译产物 `SketchName$ClassName.class` |
| sketch 根目录的 `.java` 是**顶层类** | 编译产物 `ClassName.class` |
| PDE 把 `.java` 也当标签页 | `Sketch.load()` 用 `mode.getExtensions()` 扫描根目录 |
| `PApplet.runSketch()` 可用 | 多窗口可行，已在 Maven 环境下重新确认 |
| 无头构建 | `Processing.exe cli --sketch=... --build/--run/--export` |

**弃用理由**：无法分包、无法做单元测试、构建模型怪限制多（BOM、tab、路径）。
