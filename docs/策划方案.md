# 明日方舟式关卡设计器与基础战斗 策划方案 V1.5

---

## 一、项目定位

### 1.1 一句话描述
做一个数据驱动的 2D 网格塔防原型。地图编辑器只负责静态地形；关卡编辑器负责波次和规则；运行时负责动态寻路、障碍放置、干员部署和战斗。

### 1.2 核心循环
设计地图 → 配置关卡 → 玩家编队 → 进入战斗 → 部署干员/障碍 → 敌人动态寻路 → 胜负结算。

### 1.3 当前范围
- 干员暂时无技能。
- 地形五类：红门、蓝门、可通行地面、高台、不可通行。
- 支持动态障碍：玩家可放置，改变可通行性，敌人寻路实时变化。
- 先做原型，不追求美术和完整剧情。
- 美术资源：优先检测贴图文件是否存在，存在则使用贴图，不存在则使用默认色块。

### 1.4 总体架构

采用 **Maven 标准 Java 工程 + Processing 渲染层**架构。全部功能由 Java 实现、按模块分包；Processing 的 `PApplet` 承担运行时渲染（启动动画、编辑器画面、战斗画面）；UI 控件使用 G4P。各模块在独立窗口中运行，共享同一套数据。

**工程形态：单一 Maven 工程、一套源码、两个程序入口**，共用 `common` 包。
两个入口分别在独立窗口中运行，共享同一套数据。

| 入口 | 窗口 | 模块 | 职责 | 产出/读取 |
| --- | --- | --- | --- | --- |
| **GameMain** | 启动窗 | SplashScreen | 启动动画 | —— |
| | 主窗口 | LauncherUI | 战役选择（官方/自定义）、编队、干员选择 | 读取所有配置 |
| | 窗口 3 | GameRuntime | 战斗、动态寻路、障碍、干员部署 | 读取战役+地图+关卡+干员+敌人 |
| **EditorMain** | 窗口 2 | CampaignEditor | 编辑地形、红蓝门、波次与规则 | 产出 `campaign.json`、`map_xxx.json`、`level_xxx.json` |

> **原 MapEditor（只编地形）与 LevelEditor（只编波次）已合并为 CampaignEditor。**
> 理由：做一张自定义战役是一个连贯动作（画地形 → 摆红蓝门 → 配波次 → 存盘），
> 切两个窗口会把这件事割裂。详见 §6 与 §10.2。

**技术选型：**

| 项       | 选型                                    | 说明                                       |
| -------- | --------------------------------------- | ------------------------------------------ |
| 开发工具 | IntelliJ IDEA 2025.1                    | 重构、跳转、调试、单元测试                 |
| 构建     | Maven                                   | 依赖管理 + 打包                            |
| JDK      | **17**                                  | Processing 4 要求；注意与系统默认 11 区分  |
| 渲染     | `org.processing:core:4.5.6`             | 取自 Maven 中央仓库，JAVA2D 渲染器         |
| UI 控件  | G4P 4.3.11                              | 通过项目内本地仓库 `.mvn/repo` 引入        |
| 打包     | `jpackage`（最后做）                     | 产出含内嵌 JRE 的独立应用                  |
| 测试     | JUnit 5                                 | 寻路、阻挡、费用等算法模块的单元测试       |

**为什么用 Java 工程而不是 Processing sketch：**

- Processing 的 sketch 构建模型**不支持 `package` 声明**——子目录中的 `.java` 文件会被静默忽略，`import` 会被当作第三方库导入而报错。大型项目只能把所有类平铺在同一层，无法体现分层，§10 的包结构设计无法落地；
- Maven 工程可以使用标准分包，并让 `model / view / controller / io / command / system` 各层真正成为包；
- 可以使用 JUnit 对带权 Dijkstra、阻挡判定、费用结算等算法密集模块编写单元测试，这在 sketch 模型下几乎无法进行；
- `jpackage` 可直接产出含运行时的独立应用，交付形态完整。

目录结构：

```text
YesterCar/                              ← Maven 工程根目录（即 git 仓库根）
  pom.xml
  .mvn/
    maven.config                        ← 固定项目内本地仓库 .mvn/repo
    repo/                               ← 项目内本地仓库（G4P 等，不入库）
  tools/                                ← 构建脚本
  third_party/G4P/                      ← G4P 4.3.11 官方完整包（必须入库）
  src/main/java/com/yestercar/
    GameMain.java                       ← 程序入口 1：游戏本体
    EditorMain.java                     ← 程序入口 2：战役编辑器
    splash/                             ← 启动动画（仅游戏本体用）
    launcher/                           ← 主菜单、战役选择、编队
    campaigneditor/                     ← 战役编辑器（合并原 mapeditor + leveleditor）
    runtime/                            ← 战斗运行时
    common/                             ← 公共模块
  src/main/resources/
    data/                               ← 只读默认数据
      operators.json
      enemies.json
      textures/
    campaigns/                          ← 只读：官方战役
  src/test/java/                        ← JUnit 测试
  data/                                 ← 运行时产出（可写）
    maps/
    levels/
    campaigns/                          ← 玩家自建战役
```

> G4P 需要装入本地仓库才能解析，由 `tools/install-g4p.cmd` 完成。
> 原因与踩坑记录见 `docs/具体设计.md` §1.5-③。

**数据目录的处理**：Processing 的 sketch 有内置 `dataPath()` 自动指向 `<sketch>/data`，Maven 工程没有这个机制，因此分两类处理：

| 类别 | 位置 | 读取方式 |
| ---- | ---- | -------- |
| **只读默认数据** | `src/main/resources/data/` | classpath（`getResourceAsStream`），打包进 jar，`enemies.json`、`operators.json`、默认贴图 |
| **用户产出数据** | 工程根目录的 `data/` | 文件系统直接读写，`map_xxx.json`、`level_xxx.json`；首次运行时自动创建目录 |

两类路径统一由 `Workspace` 类解析，屏蔽「IDE 运行」与「打包后运行」的差异。

## 二、核心规则

### 2.1 地图规则

| 项       | 决策                                                  |
| -------- | ----------------------------------------------------- |
| 地图尺寸 | 玩家创建时自定义，最大 25×25，超出禁止创建            |
| 格子大小 | 默认 64px，后续可调整                                 |
| 未放置格 | `-1` 表示，实际地图设计完成后基本不会出现             |
| 地形枚举 | -1 未放置，0 不可通行，1 地面，2 高台，3 红门，4 蓝门 |
| 红门数量 | 最多 2                                                |
| 蓝门数量 | 最多 2                                                |
| 蓝门生命 | 默认 3，编辑器可改                                    |
| 蓝门失败 | 生命归零，游戏失败                                    |
| 文件版本 | 第一版就加 `version` 字段                             |

### 2.2 漏怪规则
- 怪物与蓝门中心距离 < 0.5 格 → 怪物消失，蓝门扣 1 点生命。
- 蓝门生命为 0 → 游戏失败。

### 2.3 胜利与星级
- 胜利条件：所有波次敌人消灭，且蓝门未失守。
- 星级评分：
  - 全部蓝门均未扣血 → 3 星。
  - 任一蓝门扣过血 → 2 星。
  - 失败 → 0 星。

### 2.4 费用规则

| 项       | 决策                         |
| -------- | ---------------------------- |
| 初始费用 | 默认 10，编辑器可改          |
| 每秒回费 | 1                            |
| 击杀回费 | 不回                         |
| 障碍消耗 | 3 费                         |
| 干员撤退 | 返还部署费用的 50%，向下取整 |
| 干员死亡 | 不返还                       |
| 障碍撤离 | 不返还费用                   |

### 2.5 再部署规则
- 干员生命归零前撤退 → 进入再部署冷却。
- 干员死亡 → 进入再部署冷却。
- 每个干员拥有独立的 `redeployTime`。
- 障碍物与干员共用同一个部署栏，相当于“可多次放置、可同时存在多个的干员”。
- 障碍物放下后，立刻进入全局再部署冷却。
- 全局冷却期间不能放置障碍物。
- 障碍物初始数量 9 个，每次使用减少 1，不因撤离恢复。

### 2.6 障碍物规则

| 项           | 决策                                 |
| ------------ | ------------------------------------ |
| HP           | 所有关卡统一，默认 100               |
| 阻挡数       | 30（不考虑达到上限的情况）           |
| 消耗         | 3 费 + 1 个库存                      |
| 放置格       | 可通行地面                           |
| 不可放置     | 红门、蓝门、高台、不可通行、已有单位 |
| 被摧毁       | 怪物攻击，HP 归零后消失              |
| 撤离         | 玩家主动，不返还费用，进入全局冷却   |
| 敌人穿过     | 不考虑穿过现象                       |
| 多个敌人攻击 | 允许，受阻挡数 30 限制               |
| 再部署       | 全局冷却，放下即开始计时             |

**障碍物与路径重算：**
- 障碍物状态改变（放置、摧毁、撤离）时，触发全局路径重算。
- 只有未被阻挡的敌人参与本次路径更新。
- 被阻挡的敌人继续攻击当前目标，不受影响。

### 2.7 干员阻挡规则（解释 A）
- 每个干员有 `block` 属性，表示最多同时阻挡的敌人数。
- 敌人试图进入干员所在格时：
  - 若该干员当前阻挡数 < `block` → 敌人被阻挡，停下攻击干员。
  - 若该干员当前阻挡数 >= `block` → 敌人直接穿过该格。
- 不存在“绕过”行为，敌人直接按当前规划的最短路径走。

### 2.8 干员攻击规则
- 无技能。
- 部署时选择上、下、左、右四个朝向。
- 攻击范围用格子表示，随朝向旋转。
- 近卫攻击范围：自身 + 身前一格。
- 远程/医疗攻击范围（朝右时）：

```text
2 2 2 2
1 2 2 2
2 2 2 2
```

其中 `1` 为干员，`2` 为攻击格。干员本身格子也算攻击范围。
- 敌人进入攻击范围 → 干员攻击。
- 干员攻击目标**动态调整**：每次攻击冷却结束时重新选择目标。
- 选择优先级：
  1. `FlowField.dist` 更小（离目标蓝门更近）的敌人。
  2. `dist` 相同 → 最早进入范围的敌人。
- 干员被攻击时不会反击，只攻击进入自己范围的敌人。

### 2.9 敌人攻击规则
- 被干员阻挡 → 停下攻击干员。
- 远程敌人攻击范围用格子表示，朝向随移动方向变化。
- 拐角处：前半段用原朝向，后半段用新朝向（按格子计算，对角线一半区域）。
- 玩家不可见，敌人介绍里可见。
- 敌人攻击干员的优先级：
  1. 攻击范围内最后部署的干员。
  2. 若并列 → 离自己最近的干员。

### 2.10 远程敌人范围示例

攻击自身周围一圈敌人：

```text
2 2 2
2 1 2 
2 2 2
```

朝上、下、右同理旋转。

### 2.11 动态路径规划规则

- **基本原则：** 优先走没有障碍物的通路，哪怕这条通路比有障碍物的通路更长。
- **代价定义：**
  - 静态可走 + 无动态障碍 → 代价 1。
  - 静态可走 + 有动态障碍 → 代价 `1 + PENALTY`。
  - `PENALTY = 10000`。
- **效果：** 一条 0 障碍、20 步的路径代价 20；一条 1 障碍、5 步的路径代价 10005。敌人选 0 障碍的 20 步路径。
- **多蓝门：** 每个蓝门单独计算一张带权流场，敌人绑定目标蓝门。
- **触发时机：** 玩家放置障碍物、障碍物被摧毁、玩家主动撤离障碍物。
- **参与重算的敌人：** 只有**未被阻挡**的敌人。
- **被阻挡的定义：**
  - 被干员阻挡，正在攻击干员；
  - 被障碍物阻挡，正在攻击障碍物。
- **不受重算影响：** 被阻挡的敌人锁定当前目标，直到目标消失。
- **远程敌人特殊说明：** 远程敌人可以边移动边攻击，若未被阻挡，仍属于“移动中”，需要读取最新流场。
- **目标消失后：** 被阻挡的敌人当前目标消失（干员死亡/撤退，障碍物摧毁/撤离）后，下一帧读取最新流场。

### 2.12 美术规则

- 检测贴图文件是否存在。
- 存在 → 使用贴图。
- 不存在 → 使用默认色块。
- 贴图尺寸默认 64×64。

### 2.13 编辑器规则

- 关卡编辑器第一版使用**表单**。
- UI 库使用 **G4P 4.3.11**，通过项目 `lib/` 下的本地 Maven 仓库引入，Maven 自动纳入依赖。
- 第一版必须有保存、加载、撤销。
- 重做先不做。
- 地图编辑器：左键放置，右键擦除（恢复为默认未放置背景 `-1`）。
- 关卡编辑器：读取地图作为背景，编辑波次和规则。

```json

  "version": 1,
  "name": "map_001",
  "cols": 12,

  "legend": {
    "-1": "empty",
```

- 坐标用 `col,row`，左上角为 `(0,0)`。

## 四、类设计

### 4.1 数据层

| 类           | 属性                                                         |
| ------------ | ------------------------------------------------------------ |
| TileMap      | cols, rows, tileSize, tiles[][], redDoors, blueDoors         |
| Door         | id, col, row, hp（仅蓝门用）                                 |

### 4.2 运行时

| 类        | 属性                                                         |
| --------- | ------------------------------------------------------------ |
| GameState | map, level, dynamicBlocked[][], operators, enemies, obstacles, flowFields, cost, costTimer, obstacleStock, obstacleCooldownTimer, deployHistory, gameOver, blueDoorsDamaged |
| Enemy     | id, x, y, col, row, targetBlueDoorId, hp, atk, def, speed, attackTimer, facing, targetOperator, attackingObstacle, enterRangeTime, blocked |
| Operator  | data, col, row, facing, hp, attackTimer, alive, deployOrder, redeployTimer |
| Obstacle  | col, row, hp, maxHp                                          |
| FlowField | dist[][], targetBlueDoorId, build(), getNextCol(), getNextRow() |

**Enemy 新增 `blocked` 字段：**
- `blocked = true`：被干员或障碍物阻挡，不受路径重算影响。
- `blocked = false`：移动中或边移动边攻击，受路径重算影响。

## 五、动态寻路说明

### 5.1 基本概念
流场（FlowField）是一张“每个格子到目标蓝门的带权最短路径表”。
`dist[row][col]` 表示该格到目标蓝门的最小代价。

### 5.2 代价定义

| 格子类型                     | 代价        |
| ---------------------------- | ----------- |
| 静态可走 + 无动态障碍        | 1           |
| 静态可走 + 有动态障碍        | 1 + PENALTY |
| 静态不可走（高台、不可通行） | 不可通行    |

`PENALTY = 10000`。

### 5.3 构建方式
- 每个蓝门单独构建一张流场。
- 使用 **Dijkstra** 算法，从蓝门反向计算。
- 考虑动态障碍：障碍格代价更高，从而优先选择无障碍通路。
- 可走地形：地面、红门、蓝门。
- 高台、不可通行、未放置格不可走。

### 5.4 触发重算的时机
- 玩家放置障碍物；
- 障碍物被摧毁；
- 玩家主动撤离障碍物。

### 5.5 重算后的敌人处理

| 敌人状态                       | 是否受重算影响 | 行为                             |
| ------------------------------ | -------------- | -------------------------------- |
| 正在移动，未被阻挡             | 是             | 下一帧按最新流场走               |
| 被干员阻挡，正在攻击干员       | 否             | 继续攻击干员，直到干员死亡或撤退 |
| 被障碍物阻挡，正在攻击障碍物   | 否             | 继续攻击障碍物，直到障碍物消失   |
| 远程敌人边移动边攻击，未被阻挡 | 是             | 读取最新流场，更新移动方向       |
| 刚出生                         | 是             | 直接读取最新流场                 |

### 5.6 被阻挡的定义
- 被干员阻挡：敌人试图进入干员所在格，干员阻挡数未满，敌人停下攻击干员。
- 被障碍物阻挡：敌人下一格有障碍物，停下攻击障碍物。
- 只有以上两种状态才算“被阻挡”，不受路径重算影响。
- 远程敌人若未被阻挡，即使正在攻击，也受路径重算影响。

### 5.7 攻击目标消失后
- 被阻挡的敌人当前目标消失（干员死亡/撤退，障碍物摧毁/撤离）后：
  1. 该敌人 `blocked` 置为 `false`；
  2. 下一帧读取最新流场；
  3. 若新路径上还有障碍物 → 移动过去并攻击它；
  4. 若新路径无障碍 → 直接沿路径前进；
  5. 若新路径被干员阻挡 → 停下攻击干员。

### 5.8 多蓝门处理
- 每个蓝门一张流场。
- 敌人出生时绑定目标蓝门。
- 敌人只读自己目标蓝门的流场。

## 六、编辑器设计

### 6.1 合并说明

原设计把编辑器拆成两个窗口：

| 原模块 | 原职责 | 现状 |
| --- | --- | --- |
| MapEditor（窗口 2） | 只编静态地形与红蓝门，产出 `map_xxx.json` | **合并** |
| LevelEditor（窗口 3） | 读取地图作背景，只编波次与规则，产出 `level_xxx.json` | **合并** |

**合并理由**：对玩家来说，做一张自定义战役是**一个连贯动作**——
画地形 → 摆红蓝门 → 配波次 → 存盘。切两个窗口会把这件事割裂，
且玩家要先在 A 窗口存地图、再去 B 窗口加载它，多一步无意义操作。

**合并的收益**：省掉两套窗口骨架与两套编辑状态；玩家一个按钮完成保存。
**合并的代价**：多出「门 ID 联动」三条规则（见 §6.2 末尾），这是原设计里两个窗口各自不用面对的。

### 6.2 合并后的 CampaignEditor

CampaignEditor 同时承担原 MapEditor 与 LevelEditor 的全部职责：

**地形与门（原 MapEditor 职责）：**
- 新建地图：输入列数、行数、格子像素（最大 25×25）。
- 画布：网格地图；右侧工具栏 5 种地形按钮（不可通行、地面、高台、红门、蓝门）。
- 左键放置，右键擦除（恢复为默认未放置背景 `-1`）。
- 红门/蓝门自动分配 ID，显示编号；地图校验至少一个红门、至少一个蓝门。

**波次与规则（原 LevelEditor 职责）：**
- 表单编辑关卡参数：初始费用、每秒回费、障碍费用、障碍 HP、障碍数量、障碍冷却。
- 波次列表：添加/删除波次，设置波次时间。
- 每个波次内：添加/删除出怪组，设置敌人类型、红门 ID、目标蓝门 ID、数量、间隔。
- 第一版不做可视化时间轴。

**战役层（新增）：**

- 打开官方战役时为**只读**，保存需走「另存为自定义战役」。

**通用：** 保存/加载 JSON、撤销栈、状态栏显示操作信息。

### 7.2 接口契约

**坐标系：**
- `col,row`，左上角 `(0,0)`。
- 像素坐标 = `col * tileSize + tileSize/2`。

**地形枚举：**
```text
-1  empty
 0  impassable
 1  ground
 2  high
 3  red_door
 4  blue_door
```

**静态可走判断：**
- 地形为 1（地面）、3（红门）、4（蓝门）时静态可走。
- 其他地形不可走。

**动态可走判断：**
- 静态可走 且 该格 `dynamicBlocked` 为 false。

**流场接口：**
- `build(TileMap map, int blueDoorId, boolean[][] dynamicBlocked)`：构建带权流场。
- `getNextCol(int col, int row)`：返回下一步列。
- `getNextRow(int col, int row)`：返回下一步行。

**费用接口：**
- `canAfford(int cost)`：判断费用是否足够。
- `spend(int cost)`：扣除费用。
- `refund(int cost)`：返还费用。

**事件接口：**

| 事件     | 通知谁 | 做什么                                                    |
| -------- | ------ | --------------------------------------------------------- |
| 障碍放置 | 运行时 | `dynamicBlocked=true`，库存-1，开始全局冷却，触发路径重算 |
| 障碍摧毁 | 运行时 | `dynamicBlocked=false`，移除障碍，触发路径重算            |
| 障碍撤离 | 运行时 | `dynamicBlocked=false`，移除障碍，不返还，触发路径重算    |
| 干员部署 | 运行时 | 加入 operators，记录 deployOrder                          |
| 干员撤退 | 运行时 | 移除，返还费用，进入再部署                                |
| 干员死亡 | 运行时 | 移除，不返还，进入再部署                                  |

**路径重算规则：**
- 只有 `blocked == false` 的敌人参与更新。
- `blocked == true` 的敌人继续当前行为。

**数据目录：**
分「只读默认数据」与「用户产出数据」两类，路径统一由 `Workspace` 解析（见 §1.4）。

```text
src/main/resources/data/          ← 只读，打包进 jar
  operators.json
  enemies.json
  textures/
    terrain/  enemies/  operators/

<工程根>/data/                    ← 可写，运行时产出
  maps/
  levels/
```

| Day 5 | 缓冲，验收，记录已知问题；**`jpackage` 打 exe（最后做）**   |

**最终里程碑：**
- 可交付原型：游戏本体 + 战役编辑器 + 官方战役 + 自定义战役。
- 两人可独立制作新战役（甲做图配波次，乙配敌人与数值）。
- 已知问题清单明确，后续可迭代。

### 8.7 关键路径与并行策略

**关键路径：**
1. **jar 内目录列举验证**（决定战役加载器怎么写，唯一未解决的技术风险）；
2. 地图数据类与 JSON 读写；
3. 战役结构 `Campaign` + `campaign.json`；
4. 主菜单接入与窗口互相唤起；
5. 战役编辑器波次表单与门 ID 联动；
6. 胜负与星级结算。

**并行策略：**
- 甲的路径：`双入口 → 数据类 → 编辑器骨架 → 战役 → 主菜单 → 波次表单`；
- 乙的路径：`FlowField → 敌人移动 → 障碍 → 战斗 → 阻挡与再部署`；
- **乙不必等甲**：`runtime` 只依赖 `common` 与现成的 `data/maps/map_001.json`，从 Day 1 即可并行；
- `campaigneditor` 与 `runtime` 在代码上**互不依赖**，这是并行能成立的技术保证；
- 每天至少合并一次，避免最后整合；
- 任何接口变更，必须两人同时确认并更新 JSON 样例与 `Stage1SmokeTest`。

### 8.8 风险与对策

| 风险                       | 对策                                       |
| -------------------------- | ------------------------------------------ |
| AI 生成代码接口不一致      | 先冻结接口契约，AI 生成后人工 review       |
| 表单调试耗时                | 先做最小表单，再逐步加字段；数值项一律用 `GSpinner`，省去输入校验 |
| 动态路径重算与阻挡状态冲突 | 明确只有 `blocked == false` 的敌人参与重算 |
| 阻挡与再部署边界多         | 写边界测试清单，AI 生成用例，人工验证      |
| **门 ID 联动漏做**          | 合并编辑器后新增的复杂点，三条规则见 `具体设计.md` §4.1，必须实现 |
| **jar 内目录列举不可用**    | 用 `campaigns/index.json` 索引文件替代扫描 |
| 整合太晚                   | 每日合并，第 1 周末必须跑通最小闭环        |
| 排期过紧                   | 第 4 周留 1 天缓冲；若兼职则整体顺延       |

## 九、总结

本方案定义了一个数据驱动的 2D 网格塔防原型，包含：
- **战役编辑器**：编辑静态地形、红蓝门、波次与规则，输出战役、地图、关卡 JSON。
- **游戏本体**：读取战役数据，实现带权 Dijkstra 动态寻路、动态障碍、干员部署、战斗和星级评分。
- **战役体系**：官方战役（只读，随游戏分发）与自定义战役（玩家自制，存于可写目录），两者共用同一套加载器。
- **动态路径规划**：障碍物状态改变时，对未被阻挡的敌人重新计算路径，优先走无障碍通路。
- 两人都写 Java，按功能切片分工，接口契约清晰。

**工程形态**：单一 Maven 工程、一套源码、两个程序入口（`GameMain` / `EditorMain`），
共享 `common` 包。这样既满足课程设计「多个类分解任务」的要求，也让两人协作和整合更轻松。

下一步进入 P0：抽取 `AppBoot`、实现双入口，并验证 jar 内目录列举，
详见 `docs/具体设计.md` 第 6.2 节。

# 十、类分解与包结构

## 10.1 总体原则

### 10.1.1 多类分解的可行性

本项目是标准 Maven Java 工程，天然支持多文件、多类、继承、接口与包。Processing 仅以库的形式引入（`org.processing:core`）承担渲染，不参与构建流程。程序入口只作为入口，业务逻辑全部分解到独立类中，满足课程设计对「多个类分解任务」的要求。

### 10.1.2 分包方式

根包为 `com.yestercar`，采用**模块优先、层其次**的组织方式：

```text
com.yestercar.<模块>.<层>
```

采用模块优先而非层优先：编辑器、运行时、启动器各自都有 `model` / `view`，若按层优先会全部混在同一包里，且容易出现类名冲突。

| 模块包                          | 职责                       |
| ------------------------------- | -------------------------- |
| `com.yestercar.splash`          | 启动动画（仅游戏本体用）   |
| `com.yestercar.launcher`        | 主菜单、选关、编队         |
| `com.yestercar.campaigneditor`  | 战役编辑器                 |
| `com.yestercar.runtime`         | 战斗运行时                 |
| `com.yestercar.common`          | 各模块共用的公共类         |

### 10.1.3 分层结构
各模块包内部按 MVC 思路分层：

| 层         | 职责       | 示例                          |
| ---------- | ---------- | ----------------------------- |
| model      | 数据与规则 | TileMap、Door、LevelData      |
| view       | 绘制       | GridRenderer、ToolbarView     |
| controller | 交互与流程 | EditorController              |
| io         | 保存/加载  | MapJsonIO、LevelJsonIO        |
| command    | 撤销       | PlaceTileCommand、UndoManager |
| system     | 业务系统   | CombatSystem、CostSystem      |
| util       | 工具       | GridMath、AssetManager        |

并非每个模块都需要全部七层，按实际需要设置。

### 10.1.4 程序入口（双入口）

本工程有**两个程序入口**，共用一套源码与 `common` 包：

| 入口 | 职责 |
| --- | --- |
| `com.yestercar.GameMain` | 初始化 `AppBoot` → 播放启动动画 → 打开主菜单 |
| `com.yestercar.EditorMain` | 初始化 `AppBoot` → 直接打开战役编辑器（不做启动动画） |

两者共用的启动流程抽在 `common.AppBoot`：

```java
AppBoot.prepare(Class<?> entryClass, String appName)   // 建目录 + 打印环境
AppBoot.runSelfCheck(String appName)                   // 无窗口自检
AppBoot.isCheckMode(String[] args)                     // 解析 --check
```

**交付形态**：一个 fat-jar + 参数切换，而不是两个 jar。
`pom.xml` 的 `mainClass` 指向 `GameMain`，它最先判断 `--editor` 并转发给 `EditorMain`：

```powershell
java -jar target\YesterCar.jar            # 游戏本体
java -jar target\YesterCar.jar --editor   # 战役编辑器
```

各窗口类（`LauncherApp`、`EditorApp`、`GameRuntimeApp`）继承 `PApplet`，只保留入口方法并**转发事件**给各自的控制器：

- `settings()` / `setup()`
- `draw()`
- `mousePressed()` / `mouseReleased()`
- `keyPressed()`

**窗口机制已定型**：采用 `PApplet.runSketch(String[], PApplet)`，每个模块是独立的 `PApplet` 子类
（已实测通过）。`pixelDensity(1)` 必须在 `settings()` 内调用，否则会打断渲染循环——
详见 `docs/具体设计.md` §2.4 与 §2.6。

### 10.1.5 公共模块可复用
`com.yestercar.common` 由各模块共用：

- `common`：`AppBoot`（双入口共用启动流程）
- `common.util`：`JsonUtil`、`AssetManager`、`GridMath`、`UITheme`、`AttackRange`、`Director`、`AssetPaths`
- `common.model`：`Command`、`UndoManager`、`Campaign`、`CampaignMeta`
- `common.io`：`Workspace`（路径解析）、`CampaignLoader`、`CampaignJsonIO`、`CampaignStore`

> 已实现的公共类见 `docs/具体设计.md` §2.3。

## 10.6.1 战役数据契约（新增）

战役给地图与关卡加了一层目录组织，**`map_xxx.json` 与 `level_xxx.json` 的契约完全不变**（§3.1、§3.2）。

```text
【只读】src/main/resources/campaigns/
  index.json                          ← 官方战役清单
  official_01/
    campaign.json
    maps/map_001.json
    levels/level_001.json
    textures/                         ← 可选，覆盖默认贴图

【可写】<工程根>/data/campaigns/<玩家自建战役名>/
    campaign.json
    maps/  levels/  textures/
```

`campaign.json`：

```json
{
  "version": 1,
  "id": "official_01",
  "name": "第一关：边境哨站",
  "author": "开发者",
  "description": "教学关，敌人从西侧红门进攻。",
  "levels": ["level_001"]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `version` | int | 必须为 1 |
| `id` | string | 战役标识，等于目录名 |
| `name` | string | 显示名 |
| `author` | string | 作者；官方战役固定「开发者」 |
| `description` | string | 简介，可为空字符串 |
| `levels` | string[] | 关卡名列表（**有序** = 游玩顺序），不含 `.json` 后缀 |

关卡与地图的关联沿用现有设计：`level_xxx.json` 的 `"map": "maps/map_001.json"`，
**相对于所属战役目录**解析，这样一个战役目录可直接拷贝分发。

**两类战役共用同一个 `CampaignLoader`**，差别只有「存哪」与「是否只读」：

| | 官方战役 | 自定义战役 |
| --- | --- | --- |
| 存哪 | `resources/campaigns/`（进 jar） | `data/campaigns/` |
| 能否修改 | ❌ 只读 | ✅ 可改 |

**官方战役只读的实现**：在编辑器里打开官方战役时标题栏显示 `[只读]`；
点「保存」提示是否另存为自定义战役，确认后把整个战役目录复制到 `data/campaigns/<新名>/`，
后续编辑写入副本。这样玩家改不坏原版，同时保留修改的可能性。

> ⚠️ **实现风险**：从 jar 里列举目录内容不可靠（`getResourceAsStream` 只能按名字取）。
> 因此官方战役清单用 `campaigns/index.json` 索引文件代替扫描，两种运行形态行为一致。
> 详见 `docs/具体设计.md` §2.5。

## 10.9 结论

**可以，而且应该用多个类分解。**
本项目是标准 Maven Java 工程，Processing 仅作为渲染层以库形式引入。组织方式：

- **单一工程、一套源码、两个程序入口**（`GameMain` 游戏本体 / `EditorMain` 战役编辑器）；
- 根包 `com.yestercar`，下分 `splash` / `launcher` / `campaigneditor` / `runtime` / `common` 五个模块包，**模块优先、层其次**；
- 每个模块包内部按 model / view / controller / io / command / system / util 分层；
- 公共类集中在 `com.yestercar.common`，由各模块共用；
- 用接口和设计模式组织关系。

这样既满足课程设计“多个类分解任务”的要求，也让两人协作和整合更轻松。
